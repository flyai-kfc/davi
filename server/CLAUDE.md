# CLAUDE.md — server (추론 오케스트레이터)

Python 3.12 / FastAPI. 앱이 보낸 [마스킹된 화면 + 목표]로 **다음 안내 하나**를 정하고,
음성 목표가 불완전하면 LLM으로 최대 두 질문의 구체화 계획을 생성하고, 앱이 모은 답으로 한 번만 최종화한다.
공통 규칙·도메인 용어는 루트 `../CLAUDE.md`. 방향은 `../SPEC.md`.

## 이 폴더의 책임
- **2차 마스킹 그물** — 앱 1차 마스킹이 놓친 패턴 방어. 원격 업데이트 가능(앱 재배포 불필요).
  **패턴 밖 고유명은 대상이 아니다**(`SPEC.md` §2, #360). 여기서 구조로 가려내는 길도 막혀 있다 —
  **근거는 SPEC 한 곳에만 둔다.** 논거를 복제하면 정정이 한쪽에만 남는다(루트 `CLAUDE.md`의
  HANDOFF 인용 규칙과 같은 이유 — 실제로 이 줄이 그렇게 낡았다, PR #369 리뷰).
  적용 여부는 `masking.MaskingPolicy`가 값으로 들고 `reasoning.next_step()`이 주입받는다.
  우회(`DAVI_DISABLE_PRIVACY_MASKING=true`)는 **development + loopback + 접근 토큰 없음**에서만
  기동하는 dev-only 비교 실험이며, 켜지면 raw 봉투 저장이 꺼진다(#203, `../SPEC.md` §3).
  토큰은 팀용·테스트 참가자용 **둘 다** 해당한다(#257) — 어느 하나라도 있으면 거부한다.
- **프롬프트 구성 + 가드레일** — 앱별/버전별 지식과 일반 정책을 여기 둔다. 가드는 **단일 결정 지점**으로 통합(가드끼리 덮어써 불안정했던 HANDOFF §5-4 전례 회피).
- **모델 호출** — `llm_provider.py` 한 경계 뒤에 Gemini·OpenAI·Anthropic이 있다. 공급자 교체는
  `DAVI_LLM_PROVIDER`, 모델 교체는 `DAVI_MODEL`(비우면 공급자 기본 모델). 기본은
  `gemini` + `gemini-3.5-flash-lite`이고, 나머지 기본값은 저지연 등급인 `gpt-5.6-luna`·
  `claude-haiku-4-5`다. **호출부는 어느 공급자인지 알지 않는다** — 세 호출부(next-step /
  slot-fill / app-resolution)가 각자 REST 클라이언트를 복제하던 구조를 이 경계로 합쳤다.
- **완료 검증** — `expected_result`/`evidence`를 써내게 하고, evidence가 현재 화면의 최소 두 글자
  label을 어절 경계로 인용했는지 대조해 조기 종료를 줄인다. 프롬프트는 label을 작은따옴표로
  정확히 인용하게 하며, checker는 기존 무따옴표 출력의 제한된 한국어 조사·서술격 어미와
  격조사+보조사 한 개의 결합도 받는다.
  임의의 부분 문자열과 한 글자는 거부한다(#62·#71). 충분성은 판정하지 않는다(`SPEC.md` §4).
- **음성 목표 정리** — 고정 슬롯·문자열 조건 없이 LLM 구조화 출력으로 질문 필요/goal 준비를 판정.
- **목표 앱 후보** — 전체 설치 목록 없이 일반 후보 최대 5개를 만들고 기기의 ID/status 피드백을
  무상태로 판정한다. 기기에서만 발견한 앱 정보는 받지 않는다(#102·#128).
- **에러 분류** — QUOTA/NETWORK/AUTH/SERVER/PARSE/BAD_REQUEST. 앱이 사용자에게 다르게 안내한다.
  외부 공개 프로필의 QUOTA는 `rate_limit_scope=burst|daily`로 짧은 창과 24시간 창을 구분한다.
  두 창은 한 lock에서 원자적으로 소비하고, 인메모리 daily 상태는 재시작·배포 때 초기화된다.
  외부 공개 프로필은 FastAPI 기본 문서·OpenAPI endpoint도 404로 닫는다.
- **카카오 로그인 검증·세션 발급**(`kakao_auth.py`, #165) — 앱이 받아 온 카카오 access token을
  검증(발급처 `app_id` 대조)하고 카카오 회원번호를 담은 **무상태 세션 JWT**를 발급한다.
  사용자 DB 없음. 인증 전 공개 endpoint라 dev 게이트와 별개로 **모든 프로필에서 도는**
  로그인 전용 레이트리밋이 붙는다 — 출처별 제한이 정상 사용자를,
  전역 상한이 카카오 API 소모 총량을 지킨다. 세션 토큰이 담긴 성공 응답은
  `Cache-Control: no-store`다. 직접 연결은 peer IP, Azure Container Apps ingress는
  `X-Forwarded-For`의 플랫폼 보장 **가장 오른쪽 IP만** 쓰며 인증·권한에는 쓰지 않는다.
  카카오 토큰·세션 토큰·서명 비밀·IP는 로그 금지.

## 추론 아키텍처 — 실행 → 명시적 검증 2단
1. **실행** — 현재 화면에서 다음 한 걸음.
2. **명시적 검증** — 완료 판정을 별도 단계로(`_verify_done`, #62).

**계획(sub-task) 단계는 무기한 연기됐다**(2026-08-18, `../SPEC.md` §3 비목표). PoC의 단일 스텝
반응형을 넘어선 것은 **검증 단계와 가드레일 단일 결정 지점**이지 계획이 아니다. `_plan` 스텁과
"곧 반영한다"고 말하던 TODO 둘은 #202에서 `reasoning.py`를 열며 함께 걷었다(#230 규칙 완료).

## 실행
- **`py -3.12` 고정.** 원래 근거였던 litellm은 빠졌고, 지금은 코드가 `StrEnum`·`typing.Self`
  (3.11+)를 쓴다(`../SPEC.md` §5 표와 같은 근거).
- 개인 USB 검증은 loopback+`adb reverse`, 팀 공용 검증은 같은 사설 Wi-Fi의 전용 맥북 또는
  #94 Azure Container Apps development endpoint로 접속한다(`../SPEC.md` §7). Azure는 HTTPS와
  개발 토큰을 요구하는 dev-only 예외이며 production 공개 서비스가 아니다.
- API 키는 **환경변수**. 커밋 금지. `.env`는 gitignore됨.
- `DAVI_ENV` 미설정은 로컬 호환을 위해 `development`. 제품 배포는 `production`을 명시하고
  실제 LLM + non-empty 키를 사용하며 `DAVI_DEV_ACCESS_TOKEN`을 두지 않는다. #94 Azure 공유 서버는
  debug용으로 `development`와 개발 토큰을 유지하고, release APK는 같은 resource group의 별도
  Container App에서 `production` 프로필과 세션 JWT를 쓴다(#214). 잘못된 조합은
  `config.Settings`가 import 시 거부한다.
- development를 loopback 밖에 바인딩할 때는 32자 이상 토큰이 필수다 —
  `DAVI_DEV_ACCESS_TOKEN`(팀) 또는 `DAVI_TEST_ACCESS_TOKEN`(외부 테스트 참가자) 중 하나면
  된다. **헤더는 `X-Davi-Dev-Token` 하나뿐이고 값만 다르다** — 그래서 앱에는 대응 코드가 없다.
  둘로 나눈 이유는 폐기 시점이 달라서다(테스트 종료 시 참가자 토큰만 지운다). 같은 값이면 그
  구분이 없어지므로 기동 때 거부한다. 맞은 토큰 종류는 `access_token_kind`로 로그에 남고 값은
  남지 않는다.
  공용 스크립트는 worker 하나와 팀 전체 10회/60초 제한으로 공급자 쿼터를 보호한다 —
  **이 창은 두 토큰이 공유한다.** 참가자가 여럿인 테스트에서는 창을 미리 올려 둘 것.
- 요청 로그에는 비식별 운영 메타데이터만 둔다. `goal`, 화면 label, 최근 안내, 음성 발화·대화 이력·
  대화 `session_id`, 모델의 질문/goal, 요청 본문, API 키·access token은 어떤 프로필에서도 기록하지 않는다.
- 정상 요청은 Logical Request ID/attempt와 서버 request ID로 앱→LLM 단계를 연결한다(#81).
  시도 로그는 `llm_attempt_started`/`llm_attempt_finished`이고 `provider` 필드로 공급자를 남긴다.
  정상 `/health`와 기본 access log는 남기지 않으며 IP/port·User-Agent도 보존하지 않는다.
  로그 형식은 UTC timestamp가 있는 JSON Lines다. 공용 맥 스크립트는 7일, Azure Log Analytics는
  30일 보존한다. Azure에서는 도그푸딩 device allowlist를 비워 raw 저장을 끈다.
- **픽스처 보존(#41)은 운영 로그와 별개 채널이다.** 정책 원본은 `../SPEC.md` §3
  "도그푸딩 raw 보존 정책"(대상·내용·위치·기간·접근 범위). 여기서는 경계만 재확인한다 —
  위 운영 로그의 비식별 불변식은 이 채널과 무관하게 유지되며, 비화이트리스트
  `device_id`도 로그에 남기지 않는다.

## 구조화 출력 함정 (`HANDOFF.md` §10 — 실측)

아래는 Gemini에서 실측한 것이지만 대부분 공급자와 무관하다. 공급자별로 갈리는 지점만 표시한다.
- `responseSchema.properties[*].enum`에 **빈 문자열 금지**(400 `cannot be empty`). "해당 없음"은 빈 값이 아니라 **필드 생략**(required 제외)으로.
  단 **OpenAI·Anthropic strict 모드에는 "생략"이 없다** — 모든 속성이 `required`이고 "해당 없음"은
  `null`이다. 그래서 **"해당 없음"의 표현 규약을 모델 선언에 쓰지 않는다.** 선언에 한쪽을 박으면
  다른 쪽 스키마와 정반대 지시가 한 프롬프트에 함께 들어간다(PR #62 리뷰가 금지한 패턴).
  규약은 각 변환기가 자기 표현에 맞게 덧붙인다 — `gemini_schema.py`는 "이 필드를 생략한다",
  `json_schema.py`는 "null을 넣는다". 무스키마 폴백 프롬프트(`prompt.fallback_prompt`)의
  선택 필드 문장도 같은 이유로 공급자별로 갈린다. **그 경로에는 강제하는 것이 없어서 문장이
  유일한 지시다.**
- **`propertyOrdering`이 곧 생성 순서 = 추론 순서.** 근거 필드를 앞에: `expected_result` → `evidence` → `action`. action을 먼저 두면 근거를 대충 채운다.
- 스키마 없이 프롬프트로만 요구하면 선택적 필드를 그냥 비운다(항상 `null`). **필수 필드는 스키마 `required`로 강제.**
- **스키마가 거부되면 모든 호출이 실패해 앱이 통째로 멈춘다 → 무스키마 재시도 폴백 필수.**
- 출력 상한은 **`정상 응답 최소선 + 공급자 추론 몫`으로 자동 계산한다**(#259·#103).
  next-step·앱 후보는 장문 폭주를 자르는 1024를 쓰고, 의도 해석은 `ready`와 최대 2문항·문항별
  3보기를 담는 `needs_clarification` 각각의 최대 유효 compact JSON 문자 수를 **현재 Pydantic
  `maxLength`·`maxItems`에서 파생**해 더 큰 쪽을 쓴다. 이는 실제 공급자 토크나이저의 정확한
  토큰 수를 가장하는 값이 아니라, 옛 512처럼 계약 최대보다 명백히 작은 설정을 막는 최소선이다.
  여기에 Gemini thinking budget 또는 OpenAI·Anthropic reasoning 여유분을 더한다.
  `DAVI_MAX_OUTPUT_TOKENS`는 이 합 이상으로만 덮을 수 있고 더 작으면 설정 오류다(`README.md`).
  세 operation 공급자는 FastAPI startup에서 미리 만들어 한 경로만 첫 요청부터 500이 되는 부분
  기동을 막는다. schema 400 무스키마 폴백에도 같은 상한을 쓴다.
  후보가 `finishReason=MAX_TOKENS`로 끝나면 잘린 JSON을 일반 `invalid_json`으로 뭉개지 않고
  `max_output_tokens` 진단의 PARSE 실패로 분류한다. 로그에는 후보 텍스트를 남기지 않는다.
- 후보 텍스트 추출·`MAX_TOKENS` 판별·JSON fence 제거는 `gemini_response.py`의 순수 함수로
  eval과 공유한다. HTTP 재시도, 로그, 오류 분류는 `llm_provider.py`가 세 호출부를 대신해 한다.
- 잘림·거절은 **HTTP 200으로 온다**. Gemini는 `finishReason=MAX_TOKENS`, OpenAI는
  `incomplete_details.reason`, Anthropic은 `stop_reason`이다. 셋 다 잘린 조각을 파싱해
  "계약 위반"으로 뭉개지 말고 `max_output_tokens`·`refusal` 진단의 PARSE 실패로 분류한다.
- **enum 클래스 docstring은 스키마에 실리지 않는다.** `gemini_schema`가 responseSchema에 싣는 것은
  **필드의 `description`**뿐이라, `SwipeDirection` docstring에만 있던 방향 기준이 모델에
  도달하지 않았다(#109 원인). 값의 뜻을 모델에게 말하려면 **필드 description이나 프롬프트**에
  둔다 — 그 둘은 서로 같은 뜻이어야 한다(무스키마 폴백에서 한 프롬프트에 함께 들어간다).
- **모델이 지키지 못하는 기준은 프롬프트로도 안 고쳐진다.** `direction`을 손가락 기준으로 두고
  문구 규칙까지 넣었더니(#109), 모델이 자연스러운 문장("아래로 스크롤")에 **값을 끌어다 맞춰**
  원래 맞던 값이 틀리게 바뀌었다(2026-08-17 실기기 A/B). 규칙을 더 얹기 전에 **모델이 이미
  맞히는 프레임이 무엇인지** 보고, 가능하면 계약을 그쪽으로 옮긴다(C17).
- `scroll`인데 `direction`이 빠지면 화면 메타로 앞/뒤 방향을 추측하지 않는다. 같은 schema 모드에서
  방향을 명시하도록 **한 번만 재요청**하고, 다시 빠지면 PARSE로 실패한다. 로그에는 응답 원문 대신
  `scroll_direction_missing` 진단 코드만 남긴다.
- 음성 목표 판단은 공개 wire 모델과 내부 판단 모델을 분리하고, 내부 `decision_basis`를
  `status`보다 먼저 생성한다. #316 경로는 첫 판단·최종화에서 공급자를 각각 한 번만 호출한다.
  첫 판단 계약 위반은 PARSE, 최종화 계약 위반은 재호출 없는 안전 종료다. 로그에는 고정 reason
  code만 남긴다.
- Pydantic 배열의 `min_length`/`max_length`는 Gemini `minItems`/`maxItems`로 옮긴다. 변환기는
  공용이므로 slot-fill 질문·보기뿐 아니라 app-resolution의 후보·package·label 배열에도 적용된다.
  이 변환을 바꾸면 두 계약의 생성 스키마를 함께 고정하고 실제 Gemini 수용 여부도 함께 확인한다.
- 무료 티어 rate limit: flash-lite ≈ 15 RPM / 1,000 RPD. 429 `prepayment credits are depleted`는 사용량 초과가 아니라 결제 경로 문제일 수 있다. RPD 리셋은 한국시간 17:00.

| C22 | **추론 전송은 공급자 호출당 20초·논리 작업 전체 40초·Android 전체 호출 45초로 닫고, 인증 범위+endpoint+logical ID가 같은 검증 본문은 한 작업으로 합친다(#82).** 성공만 2분·최대 256개 재전송하고 같은 ID의 다른 본문은 409, 실패는 미저장이다. next-step 재전송 본문의 동일성은 앱 구조 축과 맞춰 label·window title·node id·bounds·스크롤 위치 메타와 마지막 step의 앱 관측값(`screen_changed`·`performed`·`content_signature`)을 제외하고, 나머지 endpoint는 본문 전체를 쓴다. 과거 step과 안내 내용은 계속 비교한다. next-step/app-resolution/slot-fill 실제 공급자 호출 상한은 각각 3/2/1회다. 첫 HTTP 연결이 끊겨도 공유 작업은 즉시 취소하지 않고 hard deadline까지 계속해 retry가 합류하게 하며, 늦은 결과는 버린다. 내부 실행 pool 40개는 FastAPI sync 기본 수용량과 맞추고 테스트가 anyio 실제 default limiter와 직접 대조한다. | 앱 10초 timeout이 서버 20초 처리보다 먼저 끝나 같은 화면 호출 5건이 겹쳤다. 실패를 cache하면 같은 ID retry가 영구 실패하고, 첫 연결 종료로 작업을 취소하면 retry가 합류할 대상이 사라진다. next-step 본문 전체를 비교하면 앱이 같은 ID에서 허용한 시계·배지·정착 bounds 변화와 재전송 사이의 눌림·화면 관측 갱신을 409로 오판한다. 인메모리 dedupe는 현재 worker 1개·Azure replica 1개 불변식에서만 전역 경계다. |

### C11 화면 서명·이력 정책

**반복 카운트로 fallback을 여는 정책은 #202에서 걷혔다.** 앱서랍 전환의 조건이던
`com.sec.android.app.launcher + has_scrollable_element=false`는 **스크롤 대상이 없는 화면**과
같은 말이라, 반복을 세는 동안 나가던 scroll 두 번이 곧 #202가 없애려던 헛안내였다. 지금은
같은 화면에서 **첫 요청에** 앱서랍 전환으로 간다(아래 "scroll 대상 정책").

- 화면 서명은 package/page/IME와 요소의 순서·node id·role·bounds·클릭/편집/포커스/스크롤 상태만 포함한
  SHA-256이다. label의 원문·해시·길이는 모두 제외한다.
- label을 제외한 서명은 구조·좌표가 같고 내용만 바뀐 화면을 구분하지 못한다. 화면 동일성의
  보편적 근거로 재사용하지 않는다. **이력 안에서 같은 화면을 다시 만났는지 보는 데는 쓴다**
  (#386 — 회귀 표시와 요소 줄 `tried=`). 그 한계는 문장이 감당한다 — 두 문구가 단정하지 않는다.
  **회귀 쪽은 내용 축이 신호를 더한다**(#410): 구조가 달라도 내용 서명이 같으면 같은 화면으로
  보고, 내용까지 같으면 문구에서 "구조만 봤다"는 유보를 뺀다. 값이 없는 낡은 앱에서는 구조
  축만으로 돌던 이전 동작 그대로다. 유보를 걷는 것은 표시가 붙은 스텝이 **전부** 확인됐을
  때만이다 — 문구는 이력 전체에 하나만 나가므로 약한 쪽으로 맞춘다.
  **내용이 다르다는 것은 근거로 쓰지 않는다** — 같은 화면에서 배너가 돈 것과 목록의 다른
  항목으로 간 것이 값 안에서 구분되지 않는다. 즉 보장은 **"내용이 다르다"로는 구조가 세운
  표시를 빼지 않는다**까지다. "구조는 같은데 내용이 다른 화면"을 회귀에서 빼려면 그 변화의
  인과를 알아야 하고, 그건 기기만 관측할 수 있다(#394).
  **내용이 *같아서* 표시가 빠지는 경로는 있다.** 동일성을 「떠났다」 쪽에도 같은 규칙으로 쓰므로,
  경유한 화면이 내용으로 같으면 떠난 근거가 안 서고 표시가 안 붙는다 — 구조만 흔들린 같은
  화면을 지난 경우라 그게 맞다.
  **`tried=`에는 내용 축을 쓸 수 없다.** 그쪽은 `node_id`로 세는데 그 값은 구조가 같을 때만
  같은 요소를 가리키므로, 내용이 세우는 동일성으로는 셀 대상이 특정되지 않는다. 유보 문구가
  그대로 사는 이유가 이것이다. 응답에 실어 앱이 스텝에 붙이는 값으로도 쓴다
  (스텝 안에서는 `structure_signature`다 — 내용 기반 서명이 같은 레코드에 함께 서기 때문이다).
  막힘 fallback에 `done`은 쓰지 않는다 — 막힘을 성공으로 오인시킨다.
- 앱이 사용자에게 **실제로 표시한 안내만** 스텝으로 기록한다. 세션 중지·목표 변경·같은 목표
  재시작 때 스텝 이력을 비우며, 이전 generation의 늦은 응답은 기록·표시·`done` 처리 전에 버린다.
- 서버에는 세션 상태가 없으므로 TTL 정리 대상도 없다. 앱의 스텝 이력은 최대 10개다.
- **내용 축 서명은 `Screen.content_signature`로 함께 온다**(#410). 구조 서명이 못 보는 회귀 —
  구조가 매번 달라지는 화면에서의 A→B→A — 를 서버가 **이력 간 비교**로 잡기 위한 값이다.
  2026-08-24 SM-S921N 실측이 그 화면이다: 카카오T 상세를 오르내리는 동안 서버 구조 서명은
  매번 달랐는데(요소 수 13/14/10) 내용 서명은 같은 값으로 돌아왔다.
  **서버가 계산할 수 없다**: salt가 기기 안에만 있고 프로세스 밖으로 나가지
  않는다. 세션 generation마다 새로 만들므로 비교는 세션 안에서만 성립하고, 그것이 필요한
  전부다 — 장기 역추정 가치를 남기지 않으려고 그렇게 뒀다. 원문 label은 나가지 않는다.
  축의 정의는 기기가 정한 것을 그대로 쓴다(#380) — 서버가 다시 정의하면 같은 구분을 두
  정의로 갖게 된다.

**스텝 필드와 출처** (#270)

|---|---|---|

| `screen_hint` | 응답 `screen_summary`의 echo | 채움 |

| `screen_changed` | 앱 관측 — **요청을 보내기 직전에** 마지막 스텝을 판정한다. 화면이 바뀌었으면 `true`, 같은 화면에서 다시 묻는 중이면 `false`, 그 안내 뒤 아직 요청이 없었으면 `null`. `false`가 실리는 경로에 **눌림 확인 재질의**(#319)가 있다 — **tap** 대상을 눌렀는데 눌림 시점부터 7초 무변화면 앱이 같은 화면을 한 번 더 묻는다(눌림당 최대 1회 + 화면이 바뀌면 토큰 소멸, #39의 유일한 예외. type은 입력 중일 수 있어 제외) | 채움 |
| `performed` | 앱 관측(`PressMatch`, #319) — 판정 시점은 **클릭 이벤트가 온 순간**이다(요청 직전이 아니다 — 미루면 이벤트가 버려져 옮겨 적을 값이 없다). 안내가 나간 화면 package의 클릭만 판정한다(중지 칩·IME·셰이드 클릭 배제). `true` = 좌표·텍스트 어느 축이든 일치, `false` = **좌표 축의 확신 불일치만**(클릭 노드 중심이 대상 밖 — 텍스트 폴백의 불일치는 미탐일 수 있어 `null`. 대상이 `clickable=true`였을 때만 — #311 오탐 차단), `null` = 귀속 미확인(이벤트 없음 · source 없는 불일치 · TAP/TYPE 외 액션). `true`는 되돌리지 않고 `false`는 `true`로 덮인다. 화면이 이미 바뀐 스텝에는 적지 않는다(늦은 탭의 오귀속 창 차단) | 채움 |

**프롬프트 문장 조립** (#305 — `prompt._step_line`)

서버가 스텝당 한 줄로 편다: `- '화면'에서 '안내문'라고 안내함(대상 '라벨') — 화면이 바뀜`.
세 값 모두 요소 줄과 같은 `!r` 표기다 — **구분은 따옴표가 아니라 조사가 한다.** 안내문만
큰따옴표로 감싸 눈에 띄게 하려던 초안은 값에 따라 무너졌다(#307 리뷰 실측: 안내문이 label을
큰따옴표로 인용하면 중첩되고, `!r`은 어퍼스트로피가 든 값을 큰따옴표로 감싼다).
절 순서는 `screen_hint` → `instruction` → `target_label` → 꼬리(`performed` → `screen_changed`,
시간순 — 누름이 변화보다 앞선다)이고, 꼬리 관측이 둘이면 ` · `로 잇는다
(`— 누른 것이 확인됨 · 화면이 바뀜`). **없는 값은 그 절을 통째로 생략한다**(C10의 침묵 규약 —
"알 수 없음"을 적지 않는다. `performed=null`이 침묵인 것이 특히 중요하다 — SCROLL·DONE은
구조적으로 영원히 null이다). 빈 `instruction`은 줄을 만들지 않는다.
헤더는 `최근에 한 안내와 그 결과:`다.

- `action_type`·`direction`은 싣지 않는다 — 안내문이 같은 말을 이미 한다(C17이 값과 같은 말로
  쓰게 한다). `content_signature`도 줄에 싣지 않는다 — 해시라 사람이 읽는 문장에 담을 값이
  아니고, 서버가 이력 간 대조에 쓰고 그 **결과**만 꼬리 표시로 나간다(#410).
- `performed`의 문구("누른 것이 확인됨" / "안내한 대상이 아닌 곳을 누름")는 생산자가
  TAP·TYPE뿐이라 구체형이다 — 수행 판정이 다른 조작으로 넓어지면 스텝의 `action_type`으로
  문구를 갈라야 하고, 그 분기는 그 판정을 들여오는 변경에서 추가한다(계약 무변경).
- `target_label`은 **항상** 싣는다. `tap`에서만 안내문과 중복이고 `scroll`·`type`의 안내문에는
  대상이 들어가지 않으며, 가드레일이 대상을 바꾼 경우도 여기에만 남는다(`_resolve_scroll` 2단).
- 꼬리에 실린 관측에만 그것을 어떻게 읽을지 한 줄씩 덧붙인다(둘이 겹치면 넓은 규칙 →
  좁은 예외 순). `screen_changed=false`의 줄은 **단정하지 않는 형태다** — `false`의 원인은
  "안내가 틀렸다"와 "사용자가 아직 안 했다" 둘 다이고 서버는 구별할 수 없다. 이 값이 닿는
  경로 중 오류 백오프 재시도·미검증 `done`은 둘 다 후자가 흔하다. 확정 지시를 넣으면
  사용자가 안내를 읽는 중에 맞는 안내가 버려지고, 문구가 값을 끌어당긴 C17 · #109를
  프롬프트에서 재현한다. 눌림 표시가 실리면 침묵(null)이 "안 누름"이 아니라는 줄이 붙고,
  **`performed=true`와 `screen_changed=false`가 마지막 스텝(tap)에 겹칠 때만 단정한다**
  ("그 안내를 반복하지 말고 다른 방법을 고르세요") — "아직 안 했다"가 배제된 유일한
  조합이라서다. 정체 재질의(#319)가 이 조합을 만든다. 과거 스텝의 같은 조합은 그 뒤 진행으로
  해소됐을 수 있고, type은 눌림 확인이 "입력칸을 눌렀다"까지라 단정 근거가 못 된다.
- 이력에 label과 모델 요약이 인용되므로 머리말의 데이터 경계 문장이 그쪽까지 덮는다.

- **`screen_summary`는 화면당 한 번만 생성된다.** 안내를 쓰는 같은 호출에서 함께 쓰고, 이후로는
  앱이 `screen_hint`로 echo만 한다 — 이력에서 재생성하거나 추가 호출을 하지 않는다.
  `GuideAction`에서의 자리는 `expected_result` 다음이다: 앞에 두면 "목표만 보고 정한 최종 상태"가
  현재 화면에 끌려간다(C1 순서 규칙).
- **스텝의 텍스트 세 자리(`instruction`·`target_label`·`screen_hint`)는 2차 마스킹 대상이다.**
  셋 다 화면 label에서 온 값이고, 요약이 화면 속 고유명(장소명 등)을 인용하는 것을 실측으로
  확인했다. 이력은 화면이 넘어가도 남으므로 놓친 값이 매 요청 재전송된다.
- **`screen_changed`를 시간으로 끊지 않는다.** 정체 판정(7초)으로 `false`를 박으면 **느린
  사용자가 실패로 적힌다** — 시니어가 안내 한 줄을 읽고 따라 하는 데 7초는 흔하고, 2026-08-19
  SM-S921N 세션에서 실제로 그 상태를 봤다. 판정 시점은 값이 서버에 닿는 순간, 즉 요청을
  보내기 직전이다. `true`는 되돌리지 않는다(A→B→A 회귀를 가리는 것은 내용 서명의 몫이다).
- 이력 상한 10은 그대로다. 상세 K개 + 이전 요약의 2단 이력은 효과 측정 뒤에 본다(#270 서브 5).

### tap 대상 정책 (C20 · #311)

`tap`의 대상은 **눌렀을 때 반응하는 요소**여야 한다. 단일 결정 지점(`_apply_guardrails`)에서
가림 전제 검사(0단) 다음, scroll 교정 앞에 선다 — 대상의 `clickable=False`면 SERVER 오류로
닫고(입력칸 `editable=True`는 면제), 앱의 백오프 재질의(`retryThisScreen`)가 회복 경로다.
재선택하지 않는다(가드는 교정이지 재선택이 아니다). `enabled`는 보지 않는다 — 비활성 버튼은
별도 결정 트랙이다(C20 행). 근거·경계는 C20 행과 `_reject_unclickable_tap` docstring에 있다.

### 복사 신호 정책 (C21)

`input_text`는 **안내문(`instruction`)이 집어 말한 말**일 때만 나간다(2026-08-24 개정).
**동의를 받는 면이 안내문이기 때문이다** — 사용자는 「검색창에 '한국 미국 시차'라고 입력하세요」를
읽고 그 아래 버튼을 누르므로, 채워지는 값이 방금 읽은 말과 같으면 버튼은 눈으로 확인된 일만 한다.

**목표 문장과는 대조하지 않는다.** 검색어는 목표에 그대로 있지 않은 것이 정상이라
(`한국이랑 미국의 시차를 알고 싶어` → 사람이 실제로 치는 말은 `한국 미국 시차`) 출처를 목표로
좁히면 정상 안내에서 버튼이 사라지거나 모델이 어색한 검색어를 쓴다(실측 — 프롬프트가 강제하니
`한국이랑 미국의 시차`라고 썼다). 승인의 근거를 목표에서 안내문으로 **옮긴 것이지 없앤 것이 아니다.**

단일 결정 지점(`_apply_guardrails`)에서 가림 전제 검사(0단) 다음, tap·scroll 교정 앞에 선다 —
**그 자리여야 한다**(tap 분기가 early return이라 뒤로 내리면 tap의 값을 못 비운다). 대조에 걸리지
않으면 요청을 닫지 않고 값만 비운다(안내는 그대로 나가고 사용자는 직접 입력한다). 근거·경계는
C21 행과 `_keep_input_text_named_by_instruction` docstring에 있다.

### scroll 대상 정책 (#202)

`scroll`은 **대상을 요구한다.** 대상 없이 나가면 앱이 강조할 것을 못 찾고(`highlight miss`),
사용자가 화면 전체를 쓸어도 아무 일이 없고, 화면이 그대로라 정체로 판정된다 —
**정체에서는 서버를 다시 부르지 않으므로**(#39 — 유일한 예외인 눌림 확인 재질의(#319)는
tap 눌림이 확인된 경우라 대상 없는 scroll에는 해당 없다) 회복 경로가 없다. 서로 다른 앱에서 두 번
관측됐고 한쪽은 `has_scrollable_element=true`였다. 조건은 앱 이름이 아니라 **대상 해석 실패**다.

단일 결정 지점(`_apply_guardrails`)이 위에서 아래로 적용한다.

1. 앱이 스크롤 상태를 하나도 관측하지 않았으면(전부 `None`) 아무 판정도 하지 않는다(C10).
2. 그 방향으로 갈 수 있다고 **앱이 관측한**(`can_scroll_*`) 요소가 있으면 대상을 채운다.
   축만 아는 요소를 후보로 올리는 두 번째 단은 두지 않는다 — 앱은 스크롤 다섯 필드를 통째로
   채우거나 하나도 안 채우므로(`UiTreeSerializer.scrollStateOf`) 계약상 가능할 뿐 관측된 적이 없다.
   후보가 여럿이면 **가장 넓은 스크롤 영역**을 고른다 — 사용자는 요소가 아니라 화면을 쓴다.
   모델이 이미 유효한 대상을 골랐으면 그대로 둔다(가드는 교정이지 재선택이 아니다).
3. **페이지로 넘기는 화면은 그대로 통과시킨다.** `current_page`/`total_pages`가 관측됐고 그
   방향에 아직 넘길 쪽이 남았으면(1/2에서 오른쪽, 2/2에서 왼쪽) 대상 없이 내보낸다. 삼성 런처
   홈·앱서랍은 페이지가 여러 장이어도 scrollable 노드가 0개라(HANDOFF §3-2) **대상이 요소가
   아니라 화면 자체**이고, 앱도 이 경우 강조만 빼고 안내문은 띄운다(`highlight miss`). 판정
   근거는 프롬프트가 쓰는 것과 같은 사실이다(`prompt._page_boundary`, #217). 세로 방향과
   어긋난 쪽 번호는 통과시키지 않는다.
4. 후보가 없고 안전한 대체 행동이 있는 화면이면 그쪽으로 돌린다. 현재 유일한 대체 행동은
   실기기 근거가 있는 런처의 `open_app_drawer`다(C9) — `com.sec.android.app.launcher` +
   `has_scrollable_element=false` + page 메타 없음. 앱서랍도 앞의 두 조건이 같아 page 메타로 갈린다.
5. 그 밖에는 **틀린 안내를 내보내는 대신 SERVER 오류로 닫는다.** 계약에 "진행 불가"가 없고
   `done`은 성공 의미라 대체할 수 없다(아래 보류). 앱은 이 화면을 백오프 후 다시 물어보므로
   (`retryThisScreen`) 정체와 달리 회복 경로가 남는다. **오류 문구는 네 상황을 가른다** —
   그 방향은 이미 끝 · 스크롤 요소가 그 축으로 안 움직임 · 스크롤 요소가 있다는데 요소 목록에
   없음(수 절단 의심) · 스크롤 요소 없음. 다음 수가 서로 달라서다. **"이미 끝"은 그 방향의
   축으로 움직이는 요소가 있을 때만 쓴다** — 축을 안 보면 세로 목록 화면의 `scroll right`가
   "이미 끝"으로 나가 네 번째 상황이 첫 칸에 섞인다(#251 리뷰).

**C1 운용 규칙:** `GuideAction`의 **필드 선언 순서가 곧 `propertyOrdering`**이다
(`gemini_schema.build_response_schema()`가 뽑고 `llm.GUIDE_ACTION_SCHEMA`가 들고 있다).
필드를 재배치하면 프롬프트 동작이 바뀐다. 순서를 바꿀 땐 이유를 PR에 적을 것.

### 보류
- **tap/type/일반 앱 scroll 반복의 제품적 막힘 응답** — 현재 계약에는 "진행 불가"가 없고
  임의의 다른 행동은 안전하지 않다. `done`은 성공 완료 의미라 대체할 수 없다. 실기기 근거와
  사용자 경험 결정을 얻은 뒤 별도 action/error 계약으로 검토한다.
  **조작할 요소가 없는 화면(스플래시·로딩·대기열)은 #370이 `wait` 액션으로 따로 다룬다**(C6 개정).
  C20의 tap 가드가 증상을 바꿨을 뿐 이 빈칸을 메우지는 않는다 — 헛안내 대신 백오프 재질의가
  같은 거부를 반복한다.
- **전역 제스처 액션 중 홈·뒤로** — 앱서랍은 실기기 근거가 나와 C9로 확정했다. **홈·뒤로는 아직 근거가 없어 보류 그대로다.** HANDOFF §3-14가 "홈 누르고 위로 쓸어올리세요"를 나쁜 예로 들어 홈 조작 안내가 존재함은 알 수 있으나, 그것만으로는 액션 타입이 필요한지 알 수 없다. **미리 넣으면 모델이 쓸 데 없이 고른다** — 이 사유는 여전히 유효하니 하나씩만 올린다.
- **`UiElement.selected`** — 페이지 dot의 `selected=true`는 앱의 직렬화 단계에서 `current_page` 계산에 쓰이고 끝난다(§3-3). 서버가 raw `selected`를 볼 이유가 아직 없다.
- **`bounds` 형태를 객체로** — 지금 `list[int]` 4원소는 uiautomator 관례와 맞고 앱/eval 양쪽에서 자연스럽다. 바꿀 이유 없음.
