# eval/pingpong — 핑퐁 eval

**핑퐁**(목표 구체화) 단계만 떼어, 발화 대신 텍스트로 성능을 재는 하니스(#329).
화면 fixture 회귀를 보는 `../`의 하니스와는 대상도 실행 경로도 다르다 — 공통 규칙은 `../CLAUDE.md`.

```
① 첫 요청   [사용자 LLM] ──발화──▶ [어댑터] ──▶ 핑퐁
② 질문 1~2개 + 질문별 보기(최대 3개)  ◀───────────┘
③ 로컬 응답  사용자 LLM이 질문마다 답한다 (추가 요청 없음)
④ 두 번째 요청  같은 발화 + clarification_answers ──▶ 핑퐁
⑤ ready / unable_to_finalize
                        │
                        ▼
                  [평가자 LLM] ── 도달·진행도·위반
```

흐름은 #326이 확정한 **요청 두 번**이다. 두 번째 요청은 앱과 같이 **원래 발화를 그대로 다시
보내고** 답만 싣는다. #326 이전 형식(텍스트 질문 하나를 여러 왕복)도 계속 돈다 — 그 형식으로
뜬 기준선을 다시 재거나 비교해야 하기 때문이고, 어느 쪽인지는 어댑터가 판별한다.

이 폴더가 만드는 것은 **사용자 LLM과 평가자 LLM**이다. 핑퐁 자체는 남의 코드이고,
`pingpong_eval/sut.py` 어댑터 한 겹으로만 닿는다. 핑퐁이 여러 왕복에서 한 번에 선택지를 주는
형식으로 바뀌어도 **그 파일만 고친다** — 시나리오·채점·사용자 LLM은 형식을 모른다.

## 준비

```bash
python3 -m pip install -r requirements.txt
cp .env.example .env   # GEMINI_API_KEY(사용자), ANTHROPIC_API_KEY(평가자)
```

`.env`는 `python -m pingpong_eval`이 진입점에서 한 번 읽는다(`cli.load_env`). **셸에 이미 있는
값이 이긴다** — 한 번만 다르게 돌려 볼 때는 파일을 고치지 말고 그 창에서 환경변수를 준다.

**학교 게이트웨이를 쓰면 `PINGPONG_JUDGE_BASE_URL`이 필요하다**(`.env.example`에 값이 있다).
평가자 키가 `sk-ant-`로 시작하지 않으면 그 경우다 — 안 주면 SDK가 Anthropic 본진으로 붙어
`401 invalid x-api-key`가 난다. 사용자 LLM은 게이트웨이를 타지 않고 Google을 직접 부르므로
`GEMINI_API_KEY`는 게이트웨이 키가 아니라 Google 키다.

핑퐁은 davi 서버를 로컬에서 띄워서 쓴다. **스텁으로 띄우면 채점이 무의미하다** — 스텁은 언제나
`ready`에 발화를 그대로 goal로 돌려준다. 그래서 `/health`의 `stub_llm`이 참이면 실행이 멈춘다.

```bash
cd ../../server && DAVI_USE_STUB_LLM=false uvicorn app.main:app --no-access-log --log-config app/logging.json
```

## 실행

```bash
python3 -m pingpong_eval check
```
```bash
python3 -m pingpong_eval run --davi-repo ../..
```
```bash
python3 -m pingpong_eval run --only h07,h08 --no-judge
```
```bash
python3 -m pingpong_eval compare runs/<기존> runs/<후보> --out runs/ab.md
```

산출물은 `runs/<타임스탬프>/`(gitignore)에 `report.md` · `summary.json` · `transcripts.jsonl` · `meta.json`.
`meta.json`에는 **시나리오 파일 해시**도 박힌다 — 나중에 `judge`를 돌릴 때 파일이 바뀌었으면
멈춘다. 옛 대화를 새 정답으로 채점하면 수치는 멀쩡해 보이지만 비교할 수 없기 때문이다.
`meta.json`에 davi git sha와 두 모델 id가 박히므로, 프롬프트를 고친 뒤 같은 시나리오 파일로
다시 돌리면 A/B가 된다. `compare`는 시나리오 해시·실행 id 목록·순서·seed·요청 상한 또는
평가자 배치가 다르면 멈추고, #316 완료 조건인 **2호출 이내 ready율·goal 유효율·누락 정보
환각률·선택 편향·ready 실행당 TTS 글자 수**를 같은 표로
낸다. 선택 편향은 평가자의 `선택_강요율`과 코드가 센 `보기_선택률`을 함께 본다. goal·환각·선택
강요는 같은 평가자·시나리오 배치로 채점된 실행에서만 숫자가 나오며, 미채점은 0%가 아니라 `-`다.
새 형식은 호출 상한이 2로 고정되어 `ready율`과 `2호출 이내 ready율`이 같다. 보고서는
두 값을 따로 보여 이 구조를 숨기지 않으며, 예전·새 형식의 요청 단위가 같다고 주장하지 않는다.
시드를 생략해도 실행 시 실제 정수 seed를 한 번 생성해 meta에 남긴다. `compare`에서
`--allow-scenario-drift`로 불일치를 알고 우회하면 stderr와 출력 Markdown 양쪽에 항목을 남긴다.
예전 run을 읽을 때도 코드 지표는 저장된 transcript에서 다시 계산한다. 다만 필드가
생기기 전 run은 최초 누락 슬롯 키를 복원할 수 없으므로 누락 정보 환각률은 `-`로 남고,
그 결과만 환각률 분모에서 개별로 빼고 보고서 셀에 `n`을 표시한다. 비교 가능한 결과가
하나도 없을 때만 `-`다. TTS 길이는 안전 종료·중도 오류가
문구 단축으로 보이지 않도록 `ready`로 끝난 실행만 분모에 넣는다. 이 값은 성공 여정의
총 청취 부담이므로 질문이 줄어든 효과를 포함하며, 발화당 문구 길이 지표가 아니다.

**수치는 `../../docs/voice-goal.md` §8에 한 줄로 남긴다** — `runs/`는 gitignore라
거기 두면 사라진다. 상세는 `BASELINE.md`.

## 시나리오

`scenarios/handwritten-30.json` — 팀이 손으로 쓴 정답 문장 30개(쉬움·중간·어려움 각 10).
`slots`가 **진행도의 분모**다. 슬롯을 더 잘게 쪼개면 점수가 올라간 것처럼 보이므로,
분해를 바꿀 때는 그 전 실행과 수치를 비교하지 않는다.

`노출`이 슬롯의 성격을 가른다.

| 값 | 뜻 | 채점 |
|---|---|---|
| `처음` | 사용자가 말해 줄 수 있다 | 목표 문장에 들어가야 정확 |
| `되물음` | 제대로 물어야 정확한 값이 나온다 (h07 "딸 집" → 인천 서구) | 되묻지 않고 넘기면 누락 |
| `미상` | 사용자도 모른다 (h08 약 이름) | **지어내면 틀림, 비워 두면 정확** |

## 측정하는 것

- **도달** — 최종 goal이 정답을 담았는가 (충족/부분/실패) + 슬롯별 정확/부분/누락/틀림
- **속도** — 요청 수·질문 수·확정 실패율·응답 지연. 세는 일은 코드가 한다(`metrics.py`).
- **보기 적중률 / 자유입력** — 보기가 실제 답을 담았는가. 선택지 형식의 핵심 축이다.
- **위반** — 불필요 질문 · **질문 누락** · 고유명 환각 · 질문 반복 · 한번에 두개 · 선택 강요 ·
  앱 전문용어 · 기타 없음
- **TTS 길이** — 새 형식은 첫 질문과 최종 확인, 옛 형식은 매 질문과 최종 확인에 실제로 읽는
  문구의 글자 수. 화면용 message를 중복 집계하지 않는다.

`goal 유효`는 두 번 이내 `ready`이면서 평가자가 충족 또는 부분으로 판정한 경우다. `누락 정보
환각`은 첫 발화에 없던 슬롯을 `틀림`으로 채웠거나 대화에 없는 고유명을 만든 경우다. 선택 편향은
질문 문구의 `선택_강요`와 실제 답 중 보기 선택 비율을 갈라 남긴다 — 보기를 많이 골랐다는 사실만으로
강요라고 판정하지 않는다.

`불필요_질문`은 **정답 목표에 없는 조각을 요구한 것**이다. 2026-08-21 기준선에서 실패의
근본 원인이 이것이었고, 그때는 축이 없어 증상인 `질문_반복`으로만 잡혔다.

수치는 깨끗한 손작성 시나리오 기준의 **낙관적 상한**이다. 실기기 발화의 인식 오류와
중언부언은 여기 없다.

## 유출 통제

사용자 LLM이 정답을 통째로 뱉으면 핑퐁이 1라운드에 끝나 아무것도 측정되지 않는다.
그래서 **무엇을 숨길지는 코드가 정하고**(`user_sim.py`의 난이도별 예산), LLM은 남은 것을
자연스러운 말로 바꾸기만 한다. 그 뒤 문자열 검사로 유출을 확인하고, 새면 한 번 다시 시킨다.
