# 음성 목표 확정 — 작업 문서

작성 2026-08-07. 어르신 발화를 **의도를 정확히 정의한 목표 문장 하나**로 바꾸는 기능의 작업 문서다.
방향·범위는 `../SPEC.md`, 계약 결정은 `../server/CLAUDE.md`(C1~C13)에 있고 **이 문서가 그것들을 대체하지 않는다.**
여기 있는 것이 확정되면 SPEC·CLAUDE로 올리고 이 문서에서는 링크만 남긴다.

## 상태 표기

이 문서의 모든 항목에는 상태가 붙는다. **표기 없는 문장을 결정으로 읽지 말 것.**

| 표기 | 뜻 |
|---|---|
| **[합의]** | 팀에서 확정됐다. 바꾸려면 이 문서를 먼저 고친다. |
| **[제안]** | 제안됐고 근거도 있으나 **아직 승인되지 않았다.** 이걸 전제로 코드를 쌓기 전에 합의부터 한다. |
| **[미결]** | 논의가 필요하다. 선택지와 각각의 결과만 적어 둔다. |

## 1. 지금 main에 있는 것 (사실)

#92(`server`)·#93(`app`)로 들어왔다. **"음성인식 API만 있다"는 인식은 틀렸다** — 대화 루프까지 이미 돈다.

| 구성 | 위치 | 상태 |
|---|---|---|
| STT | `app-android/.../SpeechRecognizerHelper.kt` | 온디바이스 우선(`EXTRA_PREFER_OFFLINE`), 부분/최종 결과, RECORD_AUDIO 런타임 권한 |
| TTS | `app-android/.../TextToSpeechHelper.kt` | 질문 읽기. 실패해도 화면 문구로 흐름 유지 |
| 대화 상태 | `app-android/.../VoiceDialogueSession.kt` | user/assistant 쌍 누적, 최대 10메시지(5왕복), generation 격리, stage 머신 |
| HTTP | `app-android/.../SlotFillApiClient.kt` → `POST /v1/intent/slot-fill` | |
| 의도 해석 | `server/app/intent_resolution.py`, `intent_prompt.py` | LLM 1콜 구조화 출력, 스텁/Gemini 2구현, 스키마 400 폴백, 계약 위반 1회 교정 |
| 계약 | `server/app/schemas.py` (C13) | `SlotFillRequest{utterance, session_id, conversation_history}` → `SlotFillState{status, message, goal}` |
| 테스트 | `test_intent_resolution.py`, `test_slot_fill_api.py`, `VoiceDialogueSessionTest.kt`, `SlotFillApiClientTest.kt` | |

모델 내부 출력은 `{decision_basis, status, message, goal}` 4필드이고 `decision_basis`는 wire·로그로 나가지 않는다.
`status`는 `needs_clarification` / `ready` **2개뿐**이다.

**없는 것:**

- **완료 판정 가능성 게이트** — 프롬프트에 "안내에 꼭 필요한 정보가 없으면 질문" 정도만 있고, 완료를 판정할 수 있는 문장인지 보는 축이 없다. 지금 충분성 기준은 모델 재량이다.
- **완료 신호(done_signal)** — 관찰 가능한 종료 상태를 뽑는 필드가 없다.
- 인식 실패·무응답 복구 — `MainActivity.handleSpeechError`가 모든 오류에서 `voiceSession.cancel()`로 대화를 통째로 닫는다.
- 같은 질문 반복 방지, 음성 최종 확인("이거 맞으세요?").

**없는 것이 아니라 안 하기로 한 것 — 음성 경로의 패턴 마스킹.**
`MainActivity`·`SlotFillApiClient`·`main.py`·`intent_resolution.py` 어디에도 마스킹 호출이 없는 것은 사실이지만, **누락이 아니라 `SPEC.md` §4(#92)의 결정이다.**

> 음성 원문은 연락처 이름처럼 의미 자체가 개인 데이터일 수 있어 화면 트리의 패턴 마스킹을 그대로 적용하면 **목표가 깨진다.** … 인식된 텍스트와 이전 턴이 서버와 Gemini로 **전송됨을 전제로 하되**, 앱·서버 운영 로그, 도그푸딩 raw 저장, 픽스처에는 남기지 않는다.

완화책은 이미 구현돼 있다 — `post_slot_fill`은 `_store_raw_if_dogfood`를 부르지 않고, 요청 로그에는 `conversation_message_count`만 남으며, 교정 진단에는 고정 reason code만 남는다. `app-android/CLAUDE.md`에도 같은 내용이 있다. 여는 논의는 §4 Q7이다.

## 2. 합의된 것

**[합의] A. 슬롯 taxonomy를 만들지 않는다.**
앱 종류·행동별 고정 슬롯 목록을 두지 않고, 의도 정리를 LLM 한 콜의 구조화 출력에 맡긴다.
근거: 슬롯 taxonomy는 새 목표마다 앱·서버 계약을 키우고, #88의 규칙 기반 표식은 자연어 변형에서 오분류했다(C13).

**[합의] B. 목표 문장은 "완료를 판정할 수 있는가"를 함께 만족해야 하고, 그 판단도 LLM이 한다.**
문장이 의도를 정의하는지와 그 문장으로 완료를 판정할 수 있는지를 같은 판단에서 본다. 이것이 슬롯을 대신하는 충분성 기준이다.

**[합의] C. 새 완료 기준을 현재 `reasoning._verify_done` 구현에 맞추지 않는다.**
evidence를 화면 label과 축자 대조하는 현 방식은 이 기능의 출발점이 아니다.
**단, 이것은 임시 구현이나 스텁이 아니다** — `SPEC.md` §4의 2026-07-28 결정(#62)을 구현한 것이고 받아들인 한계 3건까지 함께 문서화돼 있다. 새 완료 기준이 이를 대체하게 되면 **`SPEC.md` §4도 함께 고친다.** 가볍게 걷어낼 수 있는 코드로 읽지 말 것.
(`SPEC.md` §10이 이를 "스텁"이라고 적고 있었다. #62 이후 낡은 서술이라 이 PR에서 함께 정정했다.)

**[합의] D. 엄밀한 판정 정책보다 배선을 먼저 구현한다.**
새로 넣는 필드는 **값만 채우고 아무것도 막지 않는다.** 안내를 차단하거나 세션을 끝내는 정책은 실사용 로그가 쌓인 뒤에 연다.
근거: SPEC §3의 관통 우선 원칙과 같다 — 부품 완성도를 각자 올리다 아무도 제품을 못 써본 전례가 있다.

**[합의] E. 확정된 목표 문장과 완료 신호는 기존 안내 세션(`NextStepRequest`)으로 그대로 흘려보낸다.**
목표 확정 단계는 별도 제품이 아니라 닫힌 루프의 앞단이다. 문장은 `goal`에, 완료 신호는 새 선택 필드에 실어 기존 파이프라인을 재사용한다. 순수 추가라 낡은 앱은 무시하면 된다(`SlotFillApiClient`·`GuideApiClient` 둘 다 `ignoreUnknownKeys = true`).

## 3. 제안 — 착수 전 합의가 필요하다

아래는 2026-08-07 논의에서 나온 분석이다. **승인되지 않았다.** 특히 작업 A1이 이 제안을 코드에 박으므로, A1 착수 전에 짧게라도 결론을 낸다.

### [제안] P1. 완료 기준은 목표 확정 시점에 전부 고정할 수 없다 (2단계)

판정기가 쥘 수 있는 것은 `[목표 문장, 지금 화면(label·package·요소)]`뿐인데, 세 지점에서 깨진다.

1. **비교 대상이 없다** — 완료가 *변화*인 목표("글씨 크게 하기", "사진 지우기"). 특히 **없어진 것은 화면에 나타나지 않는다** — 원래 없었는지 방금 지웠는지 구분할 방법이 화면 안에 없다.
2. **어휘가 다르다** — "손자한테 사진 보내기"의 종착 화면 label은 `김민수`, `오후 3:12`, `1`이다. 문장의 어느 단어도 화면에 없다. 그런데 목표 확정 시점엔 그 화면을 아직 보지 못했으므로 화면 어휘를 문장에 미리 심을 수도 없다.
3. **같은 화면이 완료 전에도 나온다** — 카톡 대화방은 보내기 전에도 후에도 대화방이다. 화면 단독으로는 "했다"와 "하려던 참이다"를 못 가른다.

따라서 확정 시점엔 **판정 타입·종착 앱·필수 행동 같은 추상 기준**만 정하고, 화면 어휘로의 결합은 **실행 시점**에 한다.

각 이유가 지목하는 추가 데이터:

| 이유 | 필요한 것 | 지금 있나 |
|---|---|---|
| 1. 변화형 목표 | 세션 시작 시점 화면 스냅샷(baseline) | 없음 |
| 2. 어휘 간극 | 2단계 바인딩 | 없음 |
| 3. 궤적 필요 | 판정기 입력에 행동 이력 | `recent_actions`가 있으나 판정에 쓰이지 않음 |
| — | 원리적 판정 불가 목표의 종료 경로 | 없음 |

### [제안] P2. 게이트는 "판정 가능한가"가 아니라 "어느 타입인가"로 묻는다

"이 문장으로 완료를 판정할 수 있냐"를 추상적으로 물으면 모델이 대충 "예"라고 한다. 대신 타입을 고르게 한다.

| 타입 | 판정 근거 | 예 | 추가로 필요한 것 |
|---|---|---|---|
| 앱 도달 | `package_name` | "카메라 열기" | 없음 |
| 요소 출현 | 현재 화면의 특정 요소 | "문자 왔나 보기" | 없음 |
| 상태 변화 | baseline 대비 변화 | "와이파이 켜기" | baseline |
| 행동 완수 | 궤적의 필수 행동 + 이후 화면 | "메시지 보내기" | 궤적 |
| 판정 불가 | — | "인터넷에서 뭐 좀 찾아보기" | 사용자 확인 종료 |

이렇게 하면 ① 타입이 안 잡히는 목표가 곧 되물을 목표이고 ② 타입마다 필요한 데이터가 달라 계약이 저절로 도출되며 ③ "판정 불가"가 실패가 아니라 정당한 종료 방식이 된다.

## 4. 미결

| # | 질문 | 선택지와 결과 |
|---|---|---|
| Q1 | **"판정 불가"를 정당한 결과로 받을 것인가** | 받으면 게이트가 느슨해지고 되묻기가 준다. 대신 "다 되셨어요?" 하고 사람에게 묻는 종료 경로가 제품에 필요하다. 강제하면 되묻기가 늘고, "뭐 좀 찾아보기" 같은 목표에서 어르신이 대답할 수 없는 질문을 받는다. **"받는다"로 정하면 §6에서 음성 최종 확인을 미루는 줄을 빼야 한다** — 그 종료 경로가 즉시 필요해지기 때문이다. |
| Q2 | 완료 판정을 매 스텝 **별도 LLM 콜**로 뺄 것인가 | 정확도 ↔ 비용·지연. 무료 티어 flash-lite ≈ 15 RPM이라 스텝마다 2콜이면 상한에 빨리 닿는다. |
| Q3 | baseline 스냅샷을 계약에 넣을 것인가 | P1의 1번을 풀려면 필요하다. 요청 크기와 세션 메모리가 는다. |
| Q4 | 되묻기 상한 5왕복이 맞나 | 현재 `VoiceDialogueSession.MAX_HISTORY_MESSAGES = 10`. 근거 없이 정한 값이다. |
| Q5 | `OUT_OF_SCOPE` 상태를 넣을 것인가 | 안내 대상이 아닌 발화("오늘 날씨 어때?")용. C9의 "미리 넣으면 모델이 쓸 데 없이 고른다"가 그대로 적용되므로, 실기기에서 부딪힌 뒤 올리는 쪽이 이 저장소의 전례와 맞다. |
| Q6 | `slot-fill` 네이밍 | 엔드포인트가 `/v1/intent/slot-fill`, 타입이 `SlotFillRequest`/`SlotFillState`인데 프롬프트 첫 원칙은 "고정 슬롯 목록을 가정하지 마세요"다. C2에서 `action`→`action_type`을 "지금이 가장 싸다"는 이유로 개명한 전례가 있다. 미루면 굳는다. `SPEC.md` §4는 "이름을 호환성 때문에 유지한다"고 이미 적어 두었으므로, 바꾸려면 그 문장부터 고친다. |
| Q7 | **음성 경로 마스킹을 열 것인가** | `SPEC.md` §4가 "패턴 마스킹은 목표를 깨뜨린다"는 이유로 **의도적으로 제외**했고 완화책(로그·raw·픽스처 제외)은 구현돼 있다. 현재 패턴 5개(이메일·주민·카드·전화·계좌)는 **이름을 잡지 못해** SPEC이 지목한 위험은 어차피 막히지 않는 반면, 전화번호 패턴은 `"010-1234-5678한테 전화 걸어줘"`의 대상을 지워 목표를 못 만들게 한다. 계좌 패턴은 더 넓어 STT가 숫자를 띄어 쓴 발화를 광범위하게 먹는다. **여는 쪽을 택하려면 `SPEC.md` §4를 먼저 고치고**, 목표를 깨지 않는 방식(전송은 유지하되 로그·저장만 차단 / 번호를 자리표시자로 치환 후 복원 등)을 함께 설계한다. |

## 5. 작업 분해

의존은 `A1 → A2 → B3` 한 줄뿐이다. 계약 추가는 순수 추가라 낡은 앱이 무시해도 되므로 앱·서버가 동시에 움직일 수 있다.

**착수할 때 이슈 assignee를 등록한다.** 비어 있으면 집어도 되는 이슈다(루트 `CLAUDE.md`).

### 트랙 A — 서버 (의도 해석)

**A1. `server: 목표 확정 응답에 완료 신호와 판정 타입을 추가한다`** · `task, server` · 계약 변경 **O**
- **선행: §3의 P1·P2 합의.** 이 작업이 5분류를 코드에 박는다.
- `_IntentDialogueDecision`에 `completion_type`·`done_signal` 추가. 필드 순서는
  `decision_basis` → `completion_type` → `status` → `message` → `goal` → `done_signal`.
  판정 타입이 `status`를 강등시키는 근거이므로 앞에 온다(C1: 선언 순서 = `propertyOrdering` = 추론 순서).
- 타입을 못 고르면 `needs_clarification`.
- **wire까지 노출한다** — `_IntentDialogueDecision`(Gemini 내부 모델)만 고치면 B3에서 값이 오지 않아 A1을 다시 연다. `SlotFillState`와 앱 `Contract.kt`까지 포함한다.
- **[합의] D에 따라 아무것도 막지 않는다.** 값만 채운다.
- 완료:
  - pytest 계약 테스트, 스텁도 새 필드를 채울 것.
  - **`_REPAIR_GUIDANCE`에 새 reason code 항목 추가 + 각 reason의 교정 경로 테스트.** `intent_prompt.py`가 `_REPAIR_GUIDANCE[reason]`으로 직접 인덱싱하므로, `_recoverable_contract_reason`이 `done_signal_blank` 같은 새 reason을 반환하면 KeyError → 500이다. **정상 경로에선 안 터지고 모델이 계약을 어겼을 때만 터져 CI 초록으로 통과한다.**
  - **`_MAX_OUTPUT_TOKENS` 재검토 + 잘림 회귀 테스트.** 현재 512인데 `done_signal`은 자유 텍스트라 출력이 길어진다. 잘리면 `max_output_tokens` PARSE 실패이고, **공급자 호출은 요청당 2회 상한**(schema 400 폴백 + 교정 1회)이라 만회할 여유가 없다. next-step은 같은 이유로 이미 1024를 쓴다.
  - **`test_contract_drift.py` 확장.** 지금 `ActionType`·`SwipeDirection`·`ScrollAxis`·`ErrorKind` 4개만 본다. `completion_type`이 enum으로 wire에 나가면 같은 사각지대에 들어가고, **kotlinx는 모르는 값에 예외를 던진다** — 그 테스트 docstring이 설명하는 #17이 정확히 이 사고이며 당시 양쪽 테스트가 다 초록이었다. (`IntentDialogueStatus`도 이미 같은 사각지대에 있다.)

## 6. 이번엔 하지 않는 것

- **완료 판정으로 안내를 막거나 세션을 끝내는 것.** 새 필드는 값만 채운다([합의] D).
- baseline 스냅샷 계약화 (Q3 결론 전).
- 음성 최종 확인("이거 맞으세요?" 예/아니오). 지금은 확정 문장이 입력칸에 채워지고 **시작 버튼이 암묵적 확인**이다. 실기기에서 어르신이 헷갈리는 것이 관측된 뒤에 연다.
  **단 Q1을 "받는다"로 결론 내면 이 줄을 뺀다** — "판정 불가" 타입의 종료 경로가 곧 이것이라 즉시 필요해진다.
- 같은 질문 반복 방지 가드.
- 별도 완료 판정 콜 (Q2 결론 전).
- **음성 경로의 패턴 마스킹** (Q7 결론 전). `SPEC.md` §4가 의도적으로 제외한 것을 되돌리는 일이라, 열려면 SPEC부터 고친다.

## 7. 용어

- **목표 문장(goal)** — 어르신 발화에서 뽑아낸, 의도를 정확히 정의한 한 문장. `NextStepRequest.goal`로 그대로 들어간다.
- **완료 신호(done_signal)** — 그 목표가 끝났을 때 **관찰 가능한** 종료 상태. 사용자에게 읽어주지 않는 내부용이다.
- **판정 타입(completion_type)** — 완료를 무엇으로 판정하는지의 분류(§3 P2). 게이트의 실체.
- **게이트** — 목표 문장이 충분한지 판정해 부족하면 `needs_clarification`으로 강등시키는 자기검사. 슬롯을 대신한다.
- 나머지 용어(닫힌 루프, 1·2차 마스킹, 가드레일, 완료 검증 등)는 루트 `CLAUDE.md`에 있다.
