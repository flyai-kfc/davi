# 음성 목표 확정 — 작업 문서

작성 2026-08-07. 어르신 발화를 **의도를 정확히 정의한 목표 문장 하나**로 바꾸는 기능의 작업 문서다.
방향·범위는 `../SPEC.md`, 계약 결정은 `../server/CLAUDE.md`(C1~C14)에 있고 **이 문서가 그것들을 대체하지 않는다.**
여기 있는 것이 확정되면 SPEC·CLAUDE로 올리고 이 문서에서는 링크만 남긴다.

## 상태 표기

이 문서의 모든 항목에는 상태가 붙는다. **표기 없는 문장을 결정으로 읽지 말 것.**

| 표기 | 뜻 |
|---|---|
| **[합의]** | 팀에서 확정됐다. 바꾸려면 이 문서를 먼저 고친다. |
| **[제안]** | 제안됐고 근거도 있으나 **아직 승인되지 않았다.** 이걸 전제로 코드를 쌓기 전에 합의부터 한다. |
| **[미결]** | 논의가 필요하다. 선택지와 각각의 결과만 적어 둔다. |

## 1. 지금 main에 있는 것 (사실)

#92(`server`)·#93(`app`)로 들어왔다. **"음성인식 API만 있다"는 인식은 틀렸다** — 대화 루프까지 이미 돈다.

| 구성 | 위치 | 상태 |
|---|---|---|
| STT | `app-android/.../SpeechRecognizerHelper.kt` | 온디바이스 우선(`EXTRA_PREFER_OFFLINE`), 부분/최종 결과, RECORD_AUDIO 런타임 권한 |
| TTS | `app-android/.../TextToSpeechHelper.kt` | 질문 읽기. 실패해도 화면 문구로 흐름 유지 |
| 대화 상태 | `app-android/.../VoiceDialogueSession.kt` | user/assistant 쌍 누적, 최대 10메시지(5왕복), generation 격리, stage 머신 |
| HTTP | `app-android/.../SlotFillApiClient.kt` → `POST /v1/intent/slot-fill` | |
| 의도 해석 | `server/app/intent_resolution.py`, `intent_prompt.py` | LLM 1콜 구조화 출력, 스텁/Gemini 2구현, 스키마 400 폴백, 계약 위반 1회 교정 |
| 계약 | `server/app/schemas.py` (C13) | `SlotFillRequest{utterance, session_id, conversation_history}` → `SlotFillState{status, message, goal}` |
| 테스트 | `test_intent_resolution.py`, `test_slot_fill_api.py`, `VoiceDialogueSessionTest.kt`, `SlotFillApiClientTest.kt` | |

모델 내부 출력은 `{decision_basis, status, message, goal}` 4필드이고 `decision_basis`는 wire·로그로 나가지 않는다.
`status`는 `needs_clarification` / `ready` **2개뿐**이다.

**없는 것:**

- **완료 판정 가능성 게이트** — 프롬프트에 "안내에 꼭 필요한 정보가 없으면 질문" 정도만 있고, 완료를 판정할 수 있는 문장인지 보는 축이 없다. 지금 충분성 기준은 모델 재량이다.
- **완료 신호(done_signal)** — 관찰 가능한 종료 상태를 뽑는 필드가 없다.
- 인식 실패·무응답 복구 — `MainActivity.handleSpeechError`가 모든 오류에서 `voiceSession.cancel()`로 대화를 통째로 닫는다.
- 같은 질문 반복 방지, 음성 최종 확인("이거 맞으세요?").

**없는 것이 아니라 안 하기로 한 것 — 음성 경로의 패턴 마스킹.**
`MainActivity`·`SlotFillApiClient`·`main.py`·`intent_resolution.py` 어디에도 마스킹 호출이 없는 것은 사실이지만, **누락이 아니라 `SPEC.md` §4(#92)의 결정이다.**

> 음성 원문은 연락처 이름처럼 의미 자체가 개인 데이터일 수 있어 화면 트리의 패턴 마스킹을 그대로 적용하면 **목표가 깨진다.** … 인식된 텍스트와 이전 턴이 서버와 Gemini로 **전송됨을 전제로 하되**, 앱·서버 운영 로그, 도그푸딩 raw 저장, 픽스처에는 남기지 않는다.

완화책은 이미 구현돼 있다 — `post_slot_fill`은 `_store_raw_if_dogfood`를 부르지 않고, 요청 로그에는 `conversation_message_count`만 남으며, 교정 진단에는 고정 reason code만 남는다. `app-android/CLAUDE.md`에도 같은 내용이 있다. 여는 논의는 §4 Q7이다.

### 지금 도는 플로우

①~⑪이 목표 확정이고 **⑫부터가 기존 닫힌 루프**다.

```
[어르신]        [앱 (Kotlin)]                    [서버 (FastAPI)]           [Gemini]
    │
    │ ① "말로 입력" 탭
    ├──────────────▶ RECORD_AUDIO 런타임 권한
    │                VoiceDialogueSession.start()
    │                  → generation++, sessionId, stage=LISTENING
    │
    │ ② 발화        SpeechRecognizerHelper.start()
    ├──────────────▶  온디바이스 우선(EXTRA_PREFER_OFFLINE)
    │                 부분 결과는 화면에 실시간 표시
    │                onFinalResult(text)
    │                       │
    │                ③ nextRequest(text) → stage=REQUESTING
    │                   SlotFillRequest{utterance, sessionId,
    │                                   conversationHistory}
    │                       │  POST /v1/intent/slot-fill
    │                       │  + X-Davi-Logical-Request-ID (C12)
    │                       ▼
    │                                  ④ post_slot_fill
    │                                     resolve_intent()
    │                                     build_intent_prompt()
    │                                          │  구조화 출력 요청 ─────▶ ⑤
    │                                          │  ◀───────────────────
    │                                     {decision_basis, status,
    │                                      message, goal}
    │                                     ⑥ 실패 시 2단 복구:
    │                                        schema 400 → 무스키마 재시도
    │                                        계약 위반 → 1회 교정
    │                       ◀──────────  SlotFillState{status, message, goal}
    │                       │
    │                ⑦ applyResponse()
    │                   ├─ needs_clarification ─────────────┐
    │                   ├─ ready ──────────────┐            │
    │                   └─ 10메시지(5왕복) 초과 → LimitReached → 텍스트 입력 폴백
    │                                          │            │
    │ ⑧ 질문 듣기                              │      stage=SPEAKING
    │ ◀────────────────────────────────────────┼──── TTS로 message 읽기
    │                                          │      history에 (user,assistant) 쌍 누적
    │ ⑨ 다시 발화                              │      onFinished → continueListening
    ├──────────────────────────────────────────┼──── stage=LISTENING → ②로 되돌아감
    │                                          │
    │                                   ⑩ showReadyGoal()
    │ ◀──────────────────────────────────  goalInput에 goal 문장 채움
    │                                      message TTS로 읽기
    │
    │ ⑪ "시작" 탭  ← 여기가 사실상 최종 확인
    ├──────────────▶ GuideSession.start(goal)   ← ★ 문장 하나만 넘어간다
    │                 (음성 대화는 여기서 끝)
    │
    │                ⑫ 이후 기존 닫힌 루프
    │                   접근성 이벤트 → UiTreeSerializer → 1차 마스킹
    │                   → POST /v1/next-step → GuideAction → 오버레이
    │                   → 화면 변화 감지 → 반복
```

**이 그림에서 읽어야 할 것은 ⑪이다.** 문장 하나만 넘어가므로, ⑫의 완료 판정은 모델이 **매 스텝 새로 지어낸** `expected_result`로 한다. 목표 확정 단계가 만든 판단이 안내 루프에 하나도 전달되지 않는다. §5의 작업들이 뚫으려는 지점이 여기다.

마스킹의 비대칭도 이 그림에 있다 — ⑫의 화면 트리는 1·2차 마스킹을 거치지만 ②~⑥의 발화는 거치지 않는다(위 절의 결정).

## 2. 합의된 것

**[합의] A. 슬롯 taxonomy를 만들지 않는다.**
앱 종류·행동별 고정 슬롯 목록을 두지 않고, 의도 정리를 LLM 한 콜의 구조화 출력에 맡긴다.
근거: 슬롯 taxonomy는 새 목표마다 앱·서버 계약을 키우고, #88의 규칙 기반 표식은 자연어 변형에서 오분류했다(C13).

**[합의] B. 목표 문장은 "완료를 판정할 수 있는가"를 함께 만족해야 하고, 그 판단도 LLM이 한다.**
문장이 의도를 정의하는지와 그 문장으로 완료를 판정할 수 있는지를 같은 판단에서 본다. 이것이 슬롯을 대신하는 충분성 기준이다.

**[합의] C. 새 완료 기준을 현재 `reasoning._verify_done` 구현에 맞추지 않는다.**
evidence를 화면 label과 축자 대조하는 현 방식은 이 기능의 출발점이 아니다.
**단, 이것은 임시 구현이나 스텁이 아니다** — `SPEC.md` §4의 2026-07-28 결정(#62)을 구현한 것이고 받아들인 한계 3건까지 함께 문서화돼 있다. 새 완료 기준이 이를 대체하게 되면 **`SPEC.md` §4도 함께 고친다.** 가볍게 걷어낼 수 있는 코드로 읽지 말 것.
(`SPEC.md` §10이 이를 "스텁"이라고 적고 있었다. #62 이후 낡은 서술이라 이 PR에서 함께 정정했다.)

**[합의] D. 엄밀한 판정 정책보다 배선을 먼저 구현한다.**
새로 넣는 필드는 **값만 채우고 아무것도 막지 않는다.** 안내를 차단하거나 세션을 끝내는 정책은 실사용 로그가 쌓인 뒤에 연다.
근거: SPEC §3의 관통 우선 원칙과 같다 — 부품 완성도를 각자 올리다 아무도 제품을 못 써본 전례가 있다.

**[합의] E. 확정된 목표 문장과 완료 신호는 기존 안내 세션(`NextStepRequest`)으로 그대로 흘려보낸다.**
목표 확정 단계는 별도 제품이 아니라 닫힌 루프의 앞단이다. 문장은 `goal`에, 완료 신호는 새 선택 필드에 실어 기존 파이프라인을 재사용한다. 순수 추가라 낡은 앱은 무시하면 된다(`SlotFillApiClient`·`GuideApiClient` 둘 다 `ignoreUnknownKeys = true`).
(**완료 신호 부분은 §3 P1·P2 승인이 선행 조건이다.** 기존 파이프라인을 재사용한다는 원칙 자체는 그와 무관하게 유효하다.)

## 3. 제안 — 착수 전 합의가 필요하다

아래는 2026-08-07 논의에서 나온 분석이다. **승인되지 않았다.** 특히 작업 W5가 이 제안을 코드에 박으므로, W5 착수 전에 짧게라도 결론을 낸다(§5의 결정 회의).

### [제안] P1. 완료 기준은 목표 확정 시점에 전부 고정할 수 없다 (2단계)

판정기가 쥘 수 있는 것은 `[목표 문장, 지금 화면(label·package·요소)]`뿐인데, 세 지점에서 깨진다.

1. **비교 대상이 없다** — 완료가 *변화*인 목표("글씨 크게 하기", "사진 지우기"). 특히 **없어진 것은 화면에 나타나지 않는다** — 원래 없었는지 방금 지웠는지 구분할 방법이 화면 안에 없다.
2. **어휘가 다르다** — "손자한테 사진 보내기"의 종착 화면 label은 `김민수`, `오후 3:12`, `1`이다. 문장의 어느 단어도 화면에 없다. 그런데 목표 확정 시점엔 그 화면을 아직 보지 못했으므로 화면 어휘를 문장에 미리 심을 수도 없다.
3. **같은 화면이 완료 전에도 나온다** — 카톡 대화방은 보내기 전에도 후에도 대화방이다. 화면 단독으로는 "했다"와 "하려던 참이다"를 못 가른다.

따라서 확정 시점엔 **판정 타입·종착 앱·필수 행동 같은 추상 기준**만 정하고, 화면 어휘로의 결합은 **실행 시점**에 한다.

각 이유가 지목하는 추가 데이터:

| 이유 | 필요한 것 | 지금 있나 |
|---|---|---|
| 1. 변화형 목표 | 세션 시작 시점 화면 스냅샷(baseline) | 없음 |
| 2. 어휘 간극 | 2단계 바인딩 | 없음 |
| 3. 궤적 필요 | 판정기 입력에 행동 이력 | `recent_actions`가 있으나 판정에 쓰이지 않음 |
| — | 원리적 판정 불가 목표의 종료 경로 | 없음 |

### [제안] P2. 게이트는 "판정 가능한가"가 아니라 "어느 타입인가"로 묻는다

"이 문장으로 완료를 판정할 수 있냐"를 추상적으로 물으면 모델이 대충 "예"라고 한다. 대신 타입을 고르게 한다.

| 타입 | 판정 근거 | 예 | 추가로 필요한 것 |
|---|---|---|---|
| 앱 도달 | `package_name` | "카메라 열기" | 없음 |
| 요소 출현 | 현재 화면의 특정 요소 | "문자 왔나 보기" | 없음 |
| 상태 변화 | baseline 대비 변화 | "와이파이 켜기" | baseline |
| 행동 완수 | 궤적의 필수 행동 + 이후 화면 | "메시지 보내기" | 궤적 |
| 판정 불가 | — | "인터넷에서 뭐 좀 찾아보기" | 사용자 확인 종료 |

이렇게 하면 ① 타입이 안 잡히는 목표가 곧 되물을 목표이고 ② 타입마다 필요한 데이터가 달라 계약이 저절로 도출되며 ③ "판정 불가"가 실패가 아니라 정당한 종료 방식이 된다.

### [제안] P2-1. 경계 사례를 회의에서 정하고 그대로 프롬프트에 넣는다

**P2를 "승인"하는 것만으로는 부족하다.** 승인되는 것은 개념이고, 실제 분류 성능은 W5 담당자가 쓰는 프롬프트 문장이 정한다. 즉 승인 직후에 한 사람이 혼자 실질적 결정을 내리게 된다.

아래 경계 사례를 회의에서 정하면 그 결정이 팀의 것이 되고, 정한 값이 곧 프롬프트의 예시가 된다. **위 P2 표의 예시를 다시 쓰지 않는다** — 같은 예를 프롬프트에 두 번 보여주게 되고 픽스처가 새 영역을 못 덮는다.

| # | 발화 | 초안 | 왜 헷갈리나 |
|---|---|---|---|
| 1 | "손자한테 사진 보내기" | 행동 완수 | 종착 화면 label이 `김민수`·`오후 3:12`·`1`이라 **문장의 어느 단어도 화면에 없다.** §3 P1 이유 ②가 사례 안에 내장돼 있다. |
| 2 | "10만원 보내줘" | **미정** | 이체를 행동 완수(전송 눌렀나)로 볼지 상태 변화(잔액이 줄었나)로 볼지 갈린다. **선행 확인: 금융 앱이 안내 범위인지**(아래 §4 Q8). |
| 3 | "사진 지워줘" | **미정 — Q3에 종속** | 없어진 것은 화면에 나타나지 않는다. **갈리는 게 아니라 Q3의 답이 정한다** — baseline을 넣으면 상태 변화, 안 넣으면 이번 사이클 한정 판정 불가. |
| 4 | "글씨 크게 해줘" | 상태 변화 | 완료 화면에 "크게"라는 증거가 없다. baseline이 반드시 필요한 사례. |
| 5 | "소리 좀 키워줘" | 판정 불가 | **⚠️ 미검증 추정** — 볼륨은 하드웨어 키로도 바뀌고 접근성 트리에 안 나타날 것으로 **보이나 실측하지 않았다.** 맞다면 **상태가 화면 밖에 있는 경우**라 baseline이 있어도 안 잡힌다. `adb shell uiautomator dump` 한 번이면 확정된다 — 회의 전에 누가 확인하면 사례의 격이 올라간다. |
| 6 | "유튜브 좀 보려고" | 판정 불가 | "유튜브 열기"(앱 도달)로 좁혀 해석하고 싶어진다. 그런데 어르신의 의도는 열기가 아니다. |

### 파도 0 — 지금 즉시. 3명 동시 착수

**W1. `server: 의도 해석 경계를 견고화한다`** · `task, server` · 계약 변경 X
W5가 들어오기 전에 깔아 두는 안전망이다. **셋의 성격이 다르다 — 1번은 예방책이고 2·3번은 이미 있는 결함이다.** 근거를 섞어 쓰지 말 것.

- **(예방) `_REPAIR_GUIDANCE` 방어 + 집합 단언 테스트.** `intent_prompt.py`가 `_REPAIR_GUIDANCE[reason]`으로 직접 인덱싱한다. **오늘은 KeyError가 나지 않는다** — 생성 가능한 reason 7개(`{decision_basis,message,goal}` × `{_blank,_too_long}` + `status_goal_mismatch`)와 사전 키 7개가 정확히 같은 집합이라 도달 불가다. 문제는 W5가 `done_signal`을 넣는 순간이고, 그때 터지는 자리가 **정상 경로가 아니라 모델이 계약을 어겼을 때만이라 CI 초록으로 통과한다.**
  `.get()` + 기본 문구만으로는 약하다 — 새 reason이 생겨도 일반 문구로 교정을 시도하고 조용히 넘어간다. **"생성 가능한 reason 집합 ⊆ 사전 키 집합"을 단언하는 테스트를 함께 넣는다.** 그러면 W5에서 필드를 추가하는 순간 테스트가 먼저 터져 사전 갱신을 강제한다.

- **(현존 결함) `_MAX_OUTPUT_TOKENS` 512 → 계약 최대를 담는 값.** 계약이 허용하는 최대 응답이 이미 상한을 넘는다:
  `decision_basis` 300 + `message` 300(`MAX_INTENT_MESSAGE_LENGTH`) + `goal` 500(`MAX_VOICE_TEXT_LENGTH`) = **1,100자 + JSON 봉투.** 한국어 글자당 1토큰으로 보수적으로 잡으면 하한이 **1,228이라 1024로도 부족하다.** 잘리면 `max_output_tokens` PARSE 실패이고 **공급자 호출은 요청당 2회 상한**(schema 400 폴백 + 교정 1회)이라 만회할 여유가 없다.
  **next-step의 1024는 근거가 다르다** — `GuideAction`에는 필드 상한이 하나도 없어(`expected_result`·`evidence`·`instruction` 전부 `max_length` 없음) 담아야 할 "계약 최대"가 존재하지 않고, 그 값은 장문 폭주를 자르려고 고른 것이다. **요구가 다른 두 값을 맞추지 않는다.**
  완료: 하한을 **필드 상한에서 파생시키고** 상한을 그 이상으로 둔다 + **하한과 대조하는 테스트**(필드 상한이 바뀌면 함께 터진다) + 상한 근처 길이의 유효 응답이 그대로 통과하는지 확인. 숫자만 바꾸면 왜 그 값인지가 코드에서 사라져 나중에 되돌려진다 — 상수를 두 벌 유지하지 않는다는 점에서 위 `_REPAIR_GUIDANCE` 항목과 같은 설계다.

다만 **지금 작업을 만들지는 않는다.** `SPEC.md` §3이 "다음 할 일의 출처는 미리 세운 목록이 아니라 관통하다 실제로 부딪힌 실패"라고 정해 뒀고, 아직 아무것도 측정하지 않았다. 대신 W9b가 수치를 남기게 하고(§8), 그 수치를 보고 이슈를 연다. 회의에서 정할 것은 **그 수치를 볼 사람과 시점**이다.

**W9b가 유일한 출처는 아니다.** W5 담당자가 개인 실험 공간에서 프롬프트 비교를 먼저 돌릴 수 있고, 그러면 W9b보다 이른 수치가 나온다. 그 경로도 "누가·언제"에 포함해 정한다 — 개인 실험 결과가 어디에도 안 남으면 팀이 같은 실험을 다시 한다.

## 7. 용어

- **목표 문장(goal)** — 어르신 발화에서 뽑아낸, 의도를 정확히 정의한 한 문장. `NextStepRequest.goal`로 그대로 들어간다.
- **완료 신호(done_signal)** — 그 목표가 끝났을 때 **관찰 가능한** 종료 상태. 사용자에게 읽어주지 않는 내부용이다.
- **판정 타입(completion_type)** — 완료를 무엇으로 판정하는지의 분류(§3 P2). 게이트의 실체.
- **게이트** — 목표 문장이 충분한지 판정해 부족하면 `needs_clarification`으로 강등시키는 자기검사. 슬롯을 대신한다.
- 나머지 용어(닫힌 루프, 1·2차 마스킹, 가드레일, 완료 검증 등)는 루트 `CLAUDE.md`에 있다.

## 8. 측정 기록

**`eval/runs/`는 gitignore라 실행 산출물이 커밋되지 않는다.** 프롬프트를 고칠 근거가 되는 수치는 여기 한 줄로 남긴다 — 수치가 사라지면 이슈를 열 근거도 사라진다.

한 줄에 **날짜 · 무엇을 잰 것 · 픽스처 수 · 축별 점수 · 실행자**를 적는다. 개인 실험 공간에서 나온 프롬프트 비교 결과도 여기 남긴다(그러지 않으면 팀이 같은 실험을 다시 한다).

`SPEC.md` §8의 원칙이 그대로 적용된다 — **깨끗한 픽스처 기준 수치는 낙관적 상한임을 함께 적는다.**
